====================================

ชุด Skills สำหรับโปรเจกต์ Discord Bot + Supabase

วิธีเรียกใช้งาน
---------------
พิมพ์ / ตามด้วยชื่อ Skill ในช่อง Agent เช่น:

/analyze-log
/fix-error
/system-consult
/diagnose-system
/supabase-check
/discord-check
/review-code
/pre-deploy

ลำดับการใช้งานที่แนะนำ
-----------------------
1. /system-consult
   ใช้ตอนยังเป็นไอเดียหรือยังไม่แน่ใจว่าจะออกแบบระบบอย่างไร

2. /plan
   ใช้หลังจากรู้แล้วว่าจะทำอะไร เพื่อวางแผนการแก้ไข/พัฒนา

3. /goal
   ใช้เมื่อพร้อมให้ Agent ลงมือทำงานตามเป้าหมาย

4. /review-code

5. /supabase-check

6. /discord-check
   ใช้เพิ่มถ้างานแตะ Discord Bot/API/Permission/Event

7. /pre-deploy
   ใช้เป็นด่านสุดท้ายก่อน Deploy

กรณีระบบมีปัญหา:
- มี Error Log ชัดเจน → /analyze-log
- ระบบทำงานไม่ตรงที่ต้องการ แม้ไม่มี Error → /diagnose-system
- รู้ต้นเหตุแล้วและต้องการให้แก้ → /fix-error


==================================================
1. /system-consult — ที่ปรึกษาระบบ
==================================================

หน้าที่:
ช่วยคิดและออกแบบระบบก่อนเริ่มเขียนโค้ด

เหมาะกับ:
- มีไอเดียระบบใหม่
- ไม่แน่ใจว่าควรออกแบบอย่างไร
- ไม่แน่ใจว่าควรใช้ Table/Service/API แบบไหน
- ต้องเลือกระหว่างหลายแนวทาง
- ต้องการคิด User Flow และ System Flow
- ต้องการหา Edge Cases ก่อนเริ่มพัฒนา
- ต้องการประเมิน Security, Scalability และ Maintenance

ตัวอย่าง:
"อยากทำระบบเช่าห้อง Discord 99 บาท/30 วัน ควรออกแบบยังไง?"

สิ่งที่คาดหวัง:
- Architecture
- User Flow
- Data Flow
- Database Design
- Security
- Edge Cases
- Trade-offs
- Recommendation

จำง่าย:
"ยังไม่สร้าง → ขอคำปรึกษาก่อน"


==================================================
2. /plan — วางแผนการทำงาน
==================================================

หน้าที่:
เปลี่ยน Requirement ที่ชัดเจนแล้วให้เป็น Implementation Plan

เหมาะกับ:
- รู้แล้วว่าต้องการอะไร
- ต้องแก้หลายไฟล์
- Feature มีหลายขั้นตอน
- ต้องการให้ Agent สำรวจโค้ดก่อนลงมือ

ตัวอย่าง:
"จากระบบที่ออกแบบไว้ ช่วยวางแผนเพิ่มระบบเช่าห้อง"

สิ่งที่คาดหวัง:
- ไฟล์ที่เกี่ยวข้อง
- ขั้นตอน implementation
- Dependencies
- Database changes
- Testing
- Potential risks

จำง่าย:
"รู้ว่าจะทำอะไร → วางแผนว่าจะทำยังไง"


==================================================
3. /goal — ทำงานตามเป้าหมาย
==================================================

หน้าที่:
ใช้กำหนดเป้าหมายให้ Agent ลงมือทำงานจนเสร็จ

เหมาะกับ:
- Requirement ชัด
- พร้อมให้ Agent implement
- งานมีผลลัพธ์ที่ต้องทำให้เสร็จ

ตัวอย่าง:
"เพิ่มระบบ Daily Quest ตาม specification นี้ และทดสอบให้ครบ"

จำง่าย:
"พร้อมทำ → ลงมือ"


==================================================
4. /analyze-log — วิเคราะห์ Error Log
==================================================

หน้าที่:
วิเคราะห์ Error Log / Stack Trace เพื่อหาสาเหตุ โดยไม่รีบแก้โค้ด

เหมาะกับ:
- มี Error ใน Console
- มี Stack Trace
- Bot crash
- Edge Function error
- API error
- Database error
- Runtime error

มันจะ:
- แยก Error จริงออกจาก Warning/Noise
- หา Error แรกที่เป็นต้นเหตุ
- Trace stack
- ตรวจไฟล์ที่เกี่ยวข้อง
- ตรวจ DB/API/Config ถ้าเกี่ยวข้อง
- สรุป Root Cause
- เสนอวิธีแก้

ไม่เหมาะกับ:
"ระบบไม่ Error แต่ทำงานผิด"

กรณีนั้นใช้ /diagnose-system

จำง่าย:
"มี Error → หาว่าพังเพราะอะไร"


==================================================
5. /diagnose-system — วิเคราะห์ระบบที่ทำงานผิด
==================================================

หน้าที่:
วิเคราะห์ระบบที่ Implement แล้ว แต่พฤติกรรมจริงไม่ตรงกับที่ต้องการ
โดยเฉพาะกรณีไม่มี Error ชัดเจน

เหมาะกับ:
- Feature ทำงานไม่ครบ
- ทำงานบางครั้ง
- ผลลัพธ์ผิด
- User Flow ผิด
- Data Flow ผิด
- UI แสดงผิดทั้งที่ DB ถูก
- DB ไม่เปลี่ยนทั้งที่ UI เหมือนทำสำเร็จ
- ระบบดูเหมือนถูกแต่ใช้งานจริงไม่ได้
- โค้ดทำงาน แต่ไม่ตรง Requirement

มันจะเปรียบเทียบ:
Expected Behavior
vs
Actual Behavior

แล้ว Trace:
User
→ UI/Discord
→ Handler
→ Service
→ Database/API
→ Response
→ State/UI

จากนั้นหา:
- จุดที่เริ่มผิด
- Root Cause
- Evidence
- Impact
- Recommended Fix
- Verification Plan

ไม่ควรแก้โค้ดทันที

จำง่าย:
"ไม่มี Error แต่ระบบผิด → หาว่าผิดตรงไหนและทำไม"


==================================================
6. /fix-error — แก้ Error / Bug
==================================================

หน้าที่:
ใช้หลังจากรู้หรือสามารถยืนยันต้นเหตุของปัญหาได้ เพื่อแก้ไขและทดสอบ

เหมาะกับ:
- ต้องการให้ Agent แก้ Bug
- มี Root Cause ค่อนข้างชัด
- ต้องการให้แก้แล้ว Verify

Workflow:
วิเคราะห์
→ แก้ Root Cause
→ Test
→ ตรวจปัญหาเดิม
→ รายงานผล

หลักสำคัญ:
- ไม่กลบ Error
- ไม่ใส่ catch เพื่อซ่อนปัญหา
- ไม่ refactor เรื่องที่ไม่เกี่ยว
- ไม่บอกว่าแก้แล้วถ้ายังไม่ได้ Verify

จำง่าย:
"รู้ปัญหาแล้ว → ซ่อม"


==================================================
7. /review-code — ตรวจคุณภาพโค้ด
==================================================

หน้าที่:
Review โค้ดหรือ Diff เพื่อหาปัญหาที่อาจเกิดขึ้น
แม้ระบบจะยังไม่พัง

เหมาะกับ:
- Agent เพิ่งเขียน Feature เสร็จ
- ก่อน Merge
- ก่อน Production
- ต้องการตรวจ Bug ที่ซ่อนอยู่
- ต้องการตรวจ Security/Performance

ตรวจ:
1. Correctness
2. Security
3. Data Integrity
4. Error Handling
5. Regression
6. Performance
7. Maintainability

ตัวอย่าง:
"ระบบทำงานแล้ว ช่วย Review โค้ดทั้งหมดของ Feature นี้"

จำง่าย:
"โค้ดทำงานแล้ว → มีอะไรที่อาจพังไหม?"
